# imageCompress — 简单的图片压缩服务

基于 [Gin](https://gin-gonic.com/) 的图片压缩 HTTP 服务:通过接口上传一张图片,服务对它重新编码压缩(可选等比缩小),并把压缩结果直接放在响应体里返回。**全程在内存中处理,不会把任何文件写到磁盘。**

## 功能特性

- 支持 **PNG / GIF / JPEG** 三种格式(按文件真实内容识别,不看扩展名)
- PNG 以最高压缩率(`BestCompression`)重新编码;JPEG 按 `quality` 参数压缩
- 可选 `scale` 参数等比缩小图片(使用 CatmullRom 高质量缩放算法)
- **令牌桶限速**:平均约 3 请求/秒,突发上限 1,超限返回 429(见[已知问题 #5](#已知问题待修复),当前限速并不能真正省下服务器资源)
- 读取上限 8MB,防止超大请求体拖垮服务
- 响应的 `Content-Type` 由实际解码出的格式决定,不信任客户端声明

## 快速开始

环境要求:Go 1.26+(见 `go.mod`)。

```bash
# 启动服务(监听 :46939)
go run .
```

看到 gin 的启动日志后,服务就绪。注意:启动后的前 ~333ms 内请求会被限速器拒绝(429),原因见[已知问题 #6](#已知问题待修复)。

## API 说明

### POST /compress

**请求**:`multipart/form-data`,文件字段名为 `image`。

**查询参数**:

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `quality` | **是(所有格式)** | 压缩质量,1–100 的整数。设计如此:PNG/GIF 编码并不使用该值,但同样必须传,否则返回 400。只有 JPEG 的编码真正受它影响 |
| `scale` | 否 | 缩放比例,取值 `0 < scale ≤ 1`,如 `0.5` 表示宽高各缩一半;不传则不缩放。非法值(0、负数、大于 1、非数字)返回 400;`NaN` 目前会漏过校验,见[已知问题 #4](#已知问题待修复) |

**响应**:

| 状态码 | 内容 |
| --- | --- |
| 200 | 压缩后的图片字节流,`Content-Type` 为 `image/png` / `image/gif` / `image/jpeg` |
| 400 | JSON:`{"error": "原因"}`(缺少文件、参数非法、图片损坏等) |
| 429 | JSON:`{"error":"Too many requests."}`。⚠️ 当前该响应体后面还会被追加图片字节(已知问题 #5),客户端应按状态码判断,不要解析 429 的 body |

**curl 示例**:

```bash
# 压缩一张 PNG(结果存为 out.png)
curl "http://127.0.0.1:46939/compress?quality=80" -F "image=@photo.png" -o out.png

# 缩小到一半再压缩
curl "http://127.0.0.1:46939/compress?scale=0.5&quality=80" -F "image=@photo.png" -o out.png

# 压缩 JPEG(quality 对 JPEG 真正生效)
curl "http://127.0.0.1:46939/compress?quality=80" -F "image=@photo.jpg" -o out.jpg
```

提示:限速为平均 3 请求/秒,连续快速调用会收到 429,稍等约 0.4 秒重试即可。

**格式行为说明**:

- 输入 PNG → 输出 PNG;输入 GIF → 输出 GIF;输入 JPEG → 输出 JPEG
- **GIF 只保留第一帧**,动图压缩后会变成静态图
- 其他格式(BMP、WebP 等)未注册解码器,会被当作无效图片拒绝(400)

## 已知问题(待修复)

以下问题已在 `main_test.go` 中用「已知问题」标注,修复时对照测试注释即可。
此前的 #1(quality 参数误读 scale)、#2(Decode 错误未检查导致 panic)、#3(err 被遮蔽)已修复并通过测试验证。

4. **(遗留)`scale=NaN` 仍能通过校验** — `main.go:86` 写的是 `scale==math.NaN()`,但 NaN 与任何值比较都是 false(包括它自己),该判断永远不成立,当前会产出一张 1×1 图片。正确写法:`math.IsNaN(scale)`。
5. **限速 429 分支缺少 `c.Abort()`** — `main.go:56` 的 `c.JSON(429, ...)` 之后没有中止请求链,gin 会继续执行 `compressHardler`:被"拒绝"的请求照样消耗全部解码/缩放的 CPU 和内存(**限速形同虚设**),且响应体在 JSON 后面追加了图片字节。修法:`c.JSON` 后加 `c.Abort()`,或改用 `c.AbortWithStatusJSON`。
6. **服务启动初期所有请求 429** — `tokenInit` 返回的通道初始为空,第一个令牌要等首次 tick(~333ms)才产生。修法:`return ch` 前先 `ch <- struct{}{}` 预放一个令牌。

## 安全说明

**已有的防护**:

- `io.LimitReader` 限制最多读取 8MB,`MaxMultipartMemory` 限制 16MB
- 输出格式由真实解码结果决定,客户端无法通过伪造 Content-Type/扩展名让服务返回错误类型
- 不写文件到磁盘,不存在路径穿越问题
- 损坏/非图片内容返回 400,不再触发 panic(#2 已修复)
- 令牌桶限速限制了请求频率(但受 #5 影响,当前并未真正节省服务器资源)

**尚未处理的风险**(部署到非本机环境前请先解决):

- **图片炸弹(最主要风险)**:8MB 的 PNG 可以解码出超大尺寸的图(例如 20000×20000 ≈ 1.6GB 内存)。限速只限制频率,单次请求仍能打爆内存,而且在 #5 修复前连 429 的请求都会执行解码。推荐做法:解码前先用 `image.DecodeConfig` 只读尺寸,超限直接拒绝:

  ```go
  cfg, _, err := image.DecodeConfig(bytes.NewReader(src))
  if err != nil {
      // 返回 400
  }
  if cfg.Width > 4096 || cfg.Height > 4096 {
      // 返回 400:图片尺寸超限
  }
  ```

- **限速 ≠ 鉴权**:当前任何人不需要凭证就能调用接口,限速只防"刷得太快",不防"陌生人使用"。`Run(":46939")` 绑定所有网卡(0.0.0.0),公网服务器上对全网开放;且无 TLS,传输内容明文。只在本机使用可改为 `Run("127.0.0.1:46939")`;要对外服务应加上真正的身份验证(如 API Key / Token 校验中间件)、HTTPS 反向代理。
- **日志注入**:上传的文件名未经处理直接 `log.Println`,文件名里带换行符可以伪造日志行。
